## 1. Configuration Discovery & Directory Layout

`odoo-migrator` locates database configuration files in the `databases/` directory by default. This can be overridden using the `PW_MIGRATOR_CONFIG_DIR` environment variable.

```
databases/
├── BYNQ.yaml                  # Production database migration definition
├── BYNQ.draft.yaml            # Draft generated by `odoo-migrator analyze`
└── states/                    # Migration state & snapshots (persisted truth)
    ├── BYNQ.state.yaml        # Current recorded version and hop log history
    ├── BYNQ.snapshot.16.json  # Pre-hop 16 snapshot (modules, table row counts)
    └── BYNQ.snapshot.17.json  # Pre-hop 17 snapshot
```

> [!NOTE]
> Files containing `.draft` in their filename are ignored by commands that enumerate active database configurations (such as `odoo-migrator status`).

## 2. Database YAML Schema

`odoo-migrator` enforces a strict schema. Unknown keys at any level trigger validation errors to prevent typos or silent omissions.

### Top-Level Keys

| Key | Type | Required | Description |
|---|---|---|---|
| `name` | String | Yes | Short database identifier (e.g. `BYNQ`). Must match filename `<name>.yaml`. |
| `full_name` | String | No | Human-readable description or company name. Defaults to `name`. |
| `databases` | Map[Int, String] | Yes | Explicit mapping of Odoo major version to PostgreSQL database name. |
| `current_version` | Integer | Yes | Starting Odoo major version (e.g. `16`). |
| `target_version` | Integer | Yes | Target Odoo major version (e.g. `18`). |
| `hops` | Map[String, Hop] | Yes | Hop configurations keyed by `{N}_to_{M}` where `M == N + 1`. |
| `enterprise_in_addons_path` | Map[Int, Bool] | No | Records whether Enterprise code is linked into that version's addons path. |
| `notes` | String | No | Free-form operational notes, audit details, and decisions. |

#### Example Top-Level Structure

```yaml
name: BYNQ
full_name: BYNQ Logistics Pte Ltd

databases:
  16: BYQ6
  17: BYQ7
  18: BYQ8

current_version: 16
target_version: 18

enterprise_in_addons_path:
  16: true
  17: true
  18: true
```

> [!IMPORTANT]
> **No DB Name Guessing**: `databases` must explicitly define the target database name for every version the migration touches. `odoo-migrator` will never invent or fallback to generated database names.

### Hop Configuration Schema

Hop keys must strictly match the format `{N}_to_{M}` where `M = N + 1` (e.g. `16_to_17`, `17_to_18`).

| Key | Type | Default | Description |
|---|---|---|---|
| `modules_to_remove` | List[String] | `[]` | Modules to uninstall via `odoo-bin shell` on the source database prior to copying. |
| `auto_install_false` | List[String] | `[]` | Modules to set `auto_install = false` in SQL before copying. |
| `pre_sql` | List[String] | `[]` | SQL statements executed on the source database before `-u all` update. |
| `post_copy_sql` | List[String] | `[]` | SQL statements executed on the target database after DB copy, before OpenUpgrade. |
| `openupgrade_patches` | List[Entry] | `[]` | Source code patches applied to OpenUpgrade scripts during the run. |
| `modules_to_reinstall` | List[String] | `[]` | Modules to install via `odoo-bin shell` on target database after OpenUpgrade. |
| `modules_to_replace` | Map[Str, Str] | `{}` | Module renames/replacements `{old_name: new_name}` handled after OpenUpgrade. |
| `notes` | String | `""` | Detailed rationale and source backup references. |

#### Complete Hop Example

```yaml
hops:
  16_to_17:
    modules_to_remove:
      # Enterprise modules: OpenUpgrade cannot migrate EE data; removed before hop 1
      - account_accountant
      - account_asset
      - account_reports
      # Upstream removals or deprecated third-party addons
      - web_kanban_gauge
      - auto_database_backup
      - account_payment_invoice_online_payment_patch
    auto_install_false:
      - snailmail
      - iap
    pre_sql:
      - "DELETE FROM ir_ui_view WHERE arch_db ILIKE '%web_kanban_gauge%';"
    post_copy_sql:
      - "UPDATE ir_mail_server SET smtp_encryption = 'starttls' WHERE smtp_port = 587;"
    openupgrade_patches:
      # Source in patches/account_patch.py copied into OpenUpgrade target tree
      - src: account_patch.py
        dest: account/17.0.1.1/post-migration.py
    modules_to_reinstall: []
    modules_to_replace:
      old_analytics_module: new_analytics_module
    notes: |
      Source backup: BYQ6_2026-09-06_15-21-18.zip.
      Enterprise modules removed per standard ANSIS migration procedure.
```

## 3. OpenUpgrade Patches System

Occasionally, OpenUpgrade upstream scripts have bugs or require environment-specific patches. `odoo-migrator` provides safe, isolated in-flight patching:

1. **Source Location**: Custom patch files reside in `patches/` within the `odoo_migrator` package (or absolute paths).
2. **Declaration**: Defined in `openupgrade_patches` as either a mapping `{src: ..., dest: ...}` or string shorthand.
3. **Lifecycle**:
   - Before `openupgrade_run`, the target script in `OpenUpgrade_{X}.0/...` is backed up to `<script>.pw2.bak`.
   - The patch file is copied into place.
   - OpenUpgrade runs against the target database.
   - **Guaranteed Cleanup**: In a `finally` block, all backed-up files are moved back to their original state, ensuring OpenUpgrade checkouts remain clean git trees.

## 4. State Tracking & Snapshots

State files stored under `databases/states/` form the definitive ground truth of database state.

### State File (`<DB>.state.yaml`)

Written and updated automatically after every completed hop:

```yaml
current_version: 17
history:
  - hop: 16->17
    timestamp: "2026-09-07T11:45:00"
    ok: true
    log: "/opt/PW/data/migration_logs/BYNQ/20260907_114500_16_to_17.log"
    verify_summary:
      criticals: 0
      errors: 0
      warnings: 2
      openupgrade_lines: 485
      installed_modules: 64
      tables: 412
```

> [!TIP]
> When executing `chain`, `odoo-migrator` trusts the version recorded in `.state.yaml` over the static `current_version` in the YAML configuration.

### Pre-Hop Snapshot (`<DB>.snapshot.<v>.json`)

Captured directly via SQL before any mutating steps in a hop:
- **`modules`**: List of all installed module technical names.
- **`tables`**: Exact dictionary mapping every PostgreSQL table name to its row count (`SELECT count(*) FROM table`).
- **`model_modules`**: Reverse index of tables and models to owning modules extracted from `ir_model_data`.

This snapshot provides the baseline for the post-hop verification engine to detect unexpected drops or row count shrinkage.

## 5. Addon Trees & Enterprise Module Conventions

### Directory Layout & Symlinks

Workspace checkouts adhere to the standard directory layout under `PW_ROOT` (`/opt/PW`):

- **Odoo Code**: `PW.6.0/` (Odoo 16), `PW.7.0/` (Odoo 17), `PW.18.0/` (Odoo 18).
- **Enterprise Checkouts**: `16.E/`, `17.E/`, `18.E/`.
- **Addon Symlinks**: `PW_ADDONS.18.0/ENTERPRISE -> /opt/PW/18.E`.

### Enterprise Migration Policy

- **OpenUpgrade Does Not Migrate Enterprise Data**: While enterprise source code may be on the `addons_path` via symlinks, OpenUpgrade only ships migration scripts for community modules.
- **Precedent**: All Enterprise modules (`account_accountant`, `account_reports`, `account_asset`, etc.) must be uninstalled prior to the first hop (`modules_to_remove`).
- **Post-Cutover Reinstallation**: When the target version is reached, enterprise modules can be reinstalled with fresh configuration if required.

## 6. Environment Variables Reference

All credentials and dynamic paths are provided through environment variables. Secrets are never stored in version-controlled YAML files.

| Variable | Default | Purpose |
|---|---|---|
| `PW_ROOT` | `/opt/PW` | Workspace root holding Odoo version checkouts and OpenUpgrade trees. |
| `PW_PG_BIN` | `/opt/homebrew/opt/postgresql@18/bin` | Directory containing PostgreSQL client binaries (`psql`, `pg_dump`, `createdb`, `dropdb`). |
| `PW_DATA_DIR` | `/opt/PW/data` | Shared data directory for filestores, database backups, and migration logs. |
| `PW_MIGRATOR_CONFIG_DIR` | `<package>/databases` | Override path for the database YAML configurations directory. |
| `PW_DB_USER` | `wsloh` | PostgreSQL username used for database operations. |
| `PW_DB_HOST` | `127.0.0.1` | PostgreSQL server host address. |
| `PW_DB_PORT` | `5432` | PostgreSQL server port number. |
| `PW_DB_PASSWORD` | *(None)* | PostgreSQL server password (if authentication requires it). |
